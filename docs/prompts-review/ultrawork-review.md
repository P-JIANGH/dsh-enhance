# ultrawork 交付回归审查（delivery regression review）—— 交付前篇

> 性质：dsh-enhance 自有深度工作协议的出口，自主设计，MIT 许可。
> 素材来源（均非 SUL）：`lazycodex`（MIT）证据门理念、`oh-my-pi`（MIT）review/verification 纪律、DeepSeek-Reasonix（MIT）可执行 verify + inverse contract 基准做法、你的工作要求（不缩范围/不半成品）、2026-07-09 用户准则。
> 触发：主 agent 声称"完成/交付/可以了"时（或在首次回复承诺的完成点）。可由主 agent 自审，或派 reviewer agent 执行（推荐：独立过滤自我确认偏差与锚定）。
> 本稿：出口回归审查，先跑可执行 verify，再逐项核对证据；不重复执行期纪律，只核验"是否真的做到"。

<ultrawork-review>

## 用法
把下面每一项当作**检查项**：核对是否有对应**证据**（不是"我做了"，而是可观察的事实）。任一检查项无证据支撑 → 判定未通过，继续工作再回到本审查。全部通过才算完成。

## A0. 可执行验证（先跑脚本，不可跳）
- [ ] 该 work 声明的 `verify.sh`/断言脚本已实际运行（非"应该能过"）。
- [ ] verify 结果 = 可观测事实（退出码/输出），不是口头声明。
- [ ] 若 verify 对 pristine 应为红、原实现应为红：确认本交付让它变绿的唯一方式是"真的修对了"，而非改断言。
- [ ] 受保护文件（若声明了 manifest）未被改/删（哈希比对通过）。
- [ ] verify 脚本由审查方/门卫执行，非被审查任务的写 agent 自证。

## A. 需求与范围
- [ ] 交付物 = 用户要的 X，无缩范围/无演示版/无"留待以后"骨架。
- [ ] 原始需求已重读，逐条对得上交付物。
- [ ] 任何偏离已向用户说明并获确认。

## B. 规划与执行
- [ ] 计划波次、待办、验证方式已存在（非平凡任务）。
- [ ] 待办全程只有一个 in_progress，无攒批；完成即标记。
- [ ] 执行严格按计划波次，无自创顺序、无跳过验证。

## C. 证据完整（核心）
- [ ] 每个场景契约有**双证据**：测试红→绿证明 + 真实 surface 可观测结果（命令输出/接口响应/页面行为）。
- [ ] 手动 QA：改 CLI 跑过命令看输出，改接口调过看响应，改界面驱动过真实页面。
- [ ] QA 产生的资源（进程/端口/临时目录/浏览器）已全部清理。
- [ ] TDD 适用处完成红→绿；豁免项（纯格式/纯注释/依赖版本/纯重命名）写明理由。
- [ ] 提交为原子增量、模仿仓库风格；无"攒成大提交"。

## D. 禁止性声明（违反即失败）
- [ ] 无"应该能用"（未实跑）。
- [ ] 无"我加了测试"（未跑/从未红过）。
- [ ] 无"修好了"（无场景证明）。
- [ ] 无"实现完成"（场景未全绿）。
- [ ] 无删除失败测试来换绿。
- [ ] 无篡改受保护文件/特判断言来"制造通过"（遵守 inverse contract）。
- [ ] 无被指出的阻塞点未修复（若有严格审查，其 blocker 已处理）。

## E. 严格审查（如适用）
- [ ] 任务触及多文件/大改/重构/安全/被要求严格：已派审查者核对"场景契约 vs 证据"，其 blocker 已修复，非阻塞建议已记录理由。
- [ ] 独立审查者未预持主 agent 的"已完成"结论，对证据独立下判断（反锚定）。

</ultrawork-review>

> 通过后：第一响应宣布"交付回归审查通过"，并把 verify 结果 + 通过项写入**完成报告**（随轨迹持久化）；未过则列出缺失项返回继续。
